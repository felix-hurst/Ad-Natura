\section{Notation}\label{SecNotation}

The structure of the Module Guide (MG) for modules follows \cite{Parnas1984},
with adaptations for Unity game engine components and 2D geometric operations.
The mathematical notation comes from Chapter 3 of \cite{Parnas1984} and
standard computational geometry references. For instance, the symbol := is used for
assignment statements and conditional rules follow the form
\newline
$(c_1 \Rightarrow r_1 | c_2 \Rightarrow r_2 | ... | c_n \Rightarrow r_n)$.

\subsection{Derived Data Types}

The Destructible Objects module uses several derived data types: sequences, vectors, polygons, tuples, agents, and textures.

\textbf{Sequences} are lists filled with elements of the same data type, denoted as seq of T where T is the element type (ex. seq of Vector2 represents a sequence of 2D points).

\textbf{Vectors} represent 2D points or directions in space:
\begin{itemize}
\item Vector2 := $(x: \mathbb{R}, y: \mathbb{R})$
\end{itemize}

\textbf{Polygons} are sequences of vertices that form closed shapes:
\begin{itemize}
\item Polygon := seq of Vector2
\end{itemize}

\textbf{Tuples} contain a list of values and can be of different types. For example (Vector2, Vector2, $\mathbb{R}$) represents a tuple containing two 2D vectors and a real number.

\textbf{Functions} are defined by the data types of their inputs and outputs. Local functions are described by giving their type signature followed by their specification. For example:
\begin{itemize}
\item distance: Vector2 $\times$ Vector2 $\rightarrow$ $\mathbb{R}$
\end{itemize}

The following additional types are used in the Slime Mold Algorithm modules (Section~\ref{SecSMA}):
\begin{itemize}
\item \textbf{Agent} := (\textit{position} : Vector2, \textit{angle} : $\mathbb{R}$, \textit{type} : Vector4) --- Represents a single slime mold agent with its world position, heading angle in radians, and species type vector.
\item \textbf{Texture2D} --- A Unity engine type representing a 2D raster image (grid of pixel values). Used to store pheromone trail maps and attraction maps in the SMA modules.
\item \textbf{RenderTexture} --- A GPU-resident texture that can be written to by compute shaders. Used for double-buffered trail maps (\texttt{ARGBFloat} format) and multi-channel attraction maps (\texttt{RFloat} format).
\item \textbf{StructuredBuffer$\langle$Agent$\rangle$} --- A GPU buffer holding the agent array, accessed by compute shader threads in parallel.
\end{itemize}

\subsubsection{Geometric Functions}

\textbf{Side(L, P):} Determines which side of line L a point P lies on
\begin{itemize}
\item Type: (Vector2 $\times$ Vector2) $\times$ Vector2 $\rightarrow$ $\mathbb{R}$
\item Returns: positive (right), negative (left), or zero (on line)
\item Definition: $(L_{end}.x - L_{start}.x) \times (P.y - L_{start}.y) - (L_{end}.y - L_{start}.y) \times (P.x - L_{start}.x)$
\end{itemize}

\vspace{5mm}

\textbf{Area(V):} Calculates the area of a polygon using the shoelace formula
\begin{itemize}
\item Type: seq of Vector2 $\rightarrow$ $\mathbb{R}^+$
\item Definition: $\frac{1}{2}|\sum_{i=0}^{n-1}(v_i.x \times v_{i+1}.y - v_{i+1}.x \times v_i.y)|$
\end{itemize}

\vspace{5mm}

\textbf{Distance$(P_1, P_2)$:} Euclidean distance between two points
\begin{itemize}
\item Type: Vector2 $\times$ Vector2 $\rightarrow$ $\mathbb{R}^+$
\item Definition: $\sqrt{(P_2.x - P_1.x)^2 + (P_2.y - P_1.y)^2}$
\end{itemize}

\vspace{5mm}

\textbf{Normalize(v):} Converts vector to unit length
\begin{itemize}
\item Type: Vector2 $\rightarrow$ Vector2
\item Definition: $v/\|v\|$ where $\|v\| = \sqrt{v.x^2 + v.y^2}$
\end{itemize}

\vspace{5mm}

\textbf{Lerp(a, b, t):} Linear interpolation between values a and b
\begin{itemize}
\item Type: $\mathbb{R} \times \mathbb{R} \times \mathbb{R} \rightarrow \mathbb{R}$ where $t \in [0, 1]$
\item Definition: $a + (b - a) \times t$
\end{itemize}

\vspace{5mm}

\textbf{Sort\_CW(V):} Sorts vertices in clockwise order around their centroid
\begin{itemize}
\item Type: seq of Vector2 $\rightarrow$ seq of Vector2
\item Ordering based on increasing $\theta(v_i, C)$
\end{itemize}

\vspace{5mm}

\textbf{Snap$(P, p_{size})$:} Snaps point to nearest grid position
\begin{itemize}
\item Type: Vector2 $\times$ $\mathbb{R}^+ \rightarrow$ Vector2
\item Definition: $(\lfloor P.x/p_{size} + 0.5 \rfloor \times p_{size}, \lfloor P.y/p_{size} + 0.5 \rfloor \times p_{size})$
\end{itemize}

\subsection{Conditional Notation}

Conditional rules in specifications follow the format:

$(c_1 \Rightarrow r_1 | c_2 \Rightarrow r_2 | ... | c_n \Rightarrow r_n)$

where $c_i$ represents a condition and $r_i$ represents the corresponding result. The conditions are evaluated in order and the first true condition determines the result.

\section{Introduction}

Decomposing a system into modules is a commonly accepted approach to developing
software.  A module is a work assignment for a programmer or programming
team~\cite{Parnas1984}.  We advocate a decomposition
based on the principle of information hiding~\cite{Parnas1972}.  This
principle supports design for change, because the ``secrets'' that each module
hides represent likely future changes.  Design for change is valuable in SC,
where modifications are frequent, especially during initial development as the
solution space is explored.  

Our design follows the rules layed out by \cite{Parnas1984}, as follows:
\begin{itemize}
\item System details that are likely to change independently should be the
  secrets of separate modules.
\item Each data structure is implemented in only one module.
\item Any other program that requires information stored in a module's data
  structures must obtain it by calling access programs belonging to that module.
\end{itemize}

After completing the first stage of the design, the Software Requirements
Specification (SRS), the Module Guide (MG) is developed~\cite{Parnas1984}. The MG
specifies the modular structure of the system and is intended to allow both
designers and maintainers to easily identify the parts of the software.  The
potential readers of this document are as follows:

\begin{itemize}
\item New project members: This document can be a guide for a new project member
  to easily understand the overall structure and quickly find the
  relevant modules they are searching for.
\item Maintainers: The hierarchical structure of the module guide improves the
  maintainers' understanding when they need to make changes to the system. It is
  important for a maintainer to update the relevant sections of the document
  after changes have been made.
\item Designers: Once the module guide has been written, it can be used to
  check for consistency, feasibility, and flexibility. Designers can verify the
  system in various ways, such as consistency among modules, feasibility of the
  decomposition, and flexibility of the design.
\end{itemize}

The rest of the document is organized as follows. Section~\ref{SecChange} lists
the anticipated and unlikely changes of the software
requirements. Section~\ref{SecMH} summarizes the module decomposition that
was constructed according to the likely changes. Section~\ref{SecConnection}
specifies the connections between the software requirements and the
modules. Section~\ref{SecMD} gives a detailed description of the
modules. Section~\ref{SecTM} includes two traceability matrices. One checks
the completeness of the design against the requirements provided in the SRS. The
other shows the relation between anticipated changes and the modules.
Section~\ref{SecUse} describes the use relation between modules. Section~\ref{SecUI}
covers the key user interfaces the system uses. Section~\ref{SecDCP}
describes the design of communication protocols. Section~\ref{SecTimeline}
details the development timeline and team responsibilities for the project.

\subsection{Anticipated Changes} \label{SecAchange}

\subsection{Unlikely Changes} \label{SecUchange}

The module design should be as general as possible. However, a general system is
more complex. Sometimes this complexity is not necessary. Fixing some design
decisions at the system architecture stage can simplify the software design. If
these decision should later need to be changed, then many parts of the design
will potentially need to be modified. Hence, it is not intended that these
decisions will be changed.

\begin{description}
\item[\refstepcounter{ucnum} \uctheucnum\label{UC1}:] Game engine (Unity).
\item[\refstepcounter{ucnum} \uctheucnum\label{UC2}:] Dimensionality (2D).
\item[\refstepcounter{ucnum} \uctheucnum\label{UC3}:] Focus and use of physics simulation for object behaviour and world simulation.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC4}:] Requirement for real-time object destruction physics.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC5}:] The fundamental geometric representation of objects as pixel-based polygons.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC6}:] Use of entry and exit points as a basis of destructive tools.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC7}:] The partitioning of objects into two entities (original object, cut off object) per tool use.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC8}:] The coordinate system (right-handed 2D cartesian coordinates).
\item[\refstepcounter{ucnum} \uctheucnum\label{UC9}:] Use of mesh rendering techniques for displaying cut objects.
\item[\refstepcounter{ucnum} \uctheucnum\label{UC10}:] Use of GPU compute shaders for slime mold simulation.
\end{description}

\section{Connection Between Requirements and Design} \label{SecConnection}

The design of the system is intended to satisfy the requirements developed in the SRS.
In this stage, the system is decomposed into modules. The connection between requirements
and modules is listed in Table~\ref{TblRT}.

\subsection{Design Decisions}

The following design decisions are made to bridge the gap between requirements and implementation:

\vspace{5mm}
\noindent
\textbf{DD1: Dual Representation}
\newline
All cut objects have a pixelated mesh texture using
Bresenham algorithm applied to them in contrast with the smooth collision mesh even
if the cut was irregular and/or diagonal in order to ensure adherence to the visual style (R6).
\newline
\textit{Related modules: \hyperref[M12]{M12}, \hyperref[M13]{M13}}

\vspace{5mm}
\noindent
\textbf{DD2: Material Profile System} In order to meet the requirement for different cutting
behaviour on different materials (R5) a JSON-based configuration system maps material names/tags
to extendable cutting parameters (softness and strength).
\newline
\textit{Related modules: \hyperref[M9]{M9}, \hyperref[M15]{M15}}

\vspace{5mm}
\noindent
\textbf{DD3: Modular Cutting Pipeline}
\newline
Cutting object flow can be broken into the following key
phases of visualization, partitioning, mesh generation, and debris spawning thereby allowing
each phase to be optimized independently and meeting the requirement for real-time interactive
cutting (R3) in an extendable and maintainable way.
\newline
\textit{Related modules: \hyperref[M6]{M6}, \hyperref[M7]{M7}, \hyperref[M11]{M11}, \hyperref[M12]{M12}, \hyperref[M8]{M8}}

\vspace{5mm}
\noindent
\textbf{DD4: Entry-Exit Point Model}
\newline
In order for players to have a clear understanding of what
the tool destroys (R2), cuts are defined by exactly two intersection points for each object
(entry and exit) which simplifies the logic and provides clear visualization and working
feedback to the player.
\newline
\textit{Related modules: \hyperref[M6]{M6}, \hyperref[M7]{M7}}

\vspace{5mm}
\noindent
\textbf{DD5: Area-Proportional Mass}
\newline
For realistic physics behaviour after cutting (R4),
object mass is updated proportionally to the change in area, maintaining consistent density.
\newline
\textit{Related modules: \hyperref[M10]{M10}, \hyperref[M14]{M14}}

\vspace{5mm}
\noindent
\textbf{DD6: GPU-Accelerated Slime Mold Simulation}
\newline
In order to meet the requirement for real-time slime mold pathfinding (R11), the simulation is executed
on the GPU via compute shaders. 1024 agents are dispatched as 64 thread groups of 16 threads each.
Attraction sources are encoded into a single multi-channel \texttt{RenderTexture}
(\texttt{WaterAttractionMap}): the G channel stores water attraction and the R channel stores
light fear/repulsion. This single-texture design eliminates an extra texture bind and
simplifies the shader interface.
\newline
\textit{Related modules: \hyperref[M16]{M16}, \hyperref[M17]{M17}, \hyperref[M18]{M18}}

\vspace{5mm}
\noindent
\textbf{DD7: Microphone Input as Decoupled Modulation Source}
\newline
Real-time audio input from the system microphone modulates simulation parameters (evaporation,
turn speed, diffusion, sensor range, pulse frequency). The \texttt{MicrophoneInput} component
(\hyperref[M19]{M19}) is a standalone MonoBehaviour with no dependency on the simulation code.
\texttt{Slime.cs} reads mic values into per-frame local copies and modulates them without mutating
Inspector-serialized defaults. This decoupling means the mic is entirely optional: if no
\texttt{MicrophoneInput} is assigned, the simulation runs identically to its non-mic configuration.
\newline
\textit{Related modules: \hyperref[M16]{M16}, \hyperref[M19]{M19}}

\vspace{5mm}
\noindent
\textbf{DD8: Consent State Split Between CPU and GPU}
\newline
The consent/resistance system splits responsibility: the CPU (\texttt{Slime.cs}) runs the stress
accumulator and refractory timer because these require temporal state across frames, while the
GPU (\texttt{Slime.compute}) applies the resulting dampening to per-agent speed, drift, trail
deposit, and pulse amplitude because these are massively parallel per-agent or per-pixel
operations. Two float uniforms (\texttt{micStress}, \texttt{refractoryState}) bridge the two.
\newline
\textit{Related modules: \hyperref[M16]{M16}, \hyperref[M19]{M19}}

\section{Module Decomposition}\label{SecMD}

Modules are decomposed according to the principle of ``information hiding'' proposed by
Parnas et al.~\cite{Parnas1984}. The Secrets field in a module decomposition is a brief statement
of the design decision hidden by the module. The Services field specifies what the
module will do without documenting how to do it. For each module, a suggestion for
the implementing software is given under the Implemented By title. If the entry is
OS, this means that the module is provided by the operating system or by standard
programming language libraries. ProgName means the module will be implemented by
the ProgName software.

\vspace{5mm}

Only the leaf modules in the hierarchy have to be implemented. If a dash (-) is shown, this means that the module is not a leaf and will not have to be implemented. 


\subsection{Hardware Hiding Modules}

Hardware-hiding modules abstract away the details of the underlying hardware and
operating environment. Their secrets are the data structures and algorithms used to
interact with physical devices and platform-specific libraries. The modules in this
category wrap Unity's built-in engine systems for input, physics, rendering, and
collision, so that the rest of the system can remain platform-agnostic. If the game

\subsection{Software Decision Modules}

algorithms, mesh construction, physics calculations, and material-specific edge generation.
These modules are primarily stateless libraries called by higher-level modules.

\subsection{Slime Mold Algorithm Modules}\label{SecSMA}

The Slime Mold Algorithm (SMA) modules implement a GPU-accelerated agent-based simulation
inspired by the growth patterns of \textit{Physarum polycephalum}, a single-celled organism
capable of decentralized decision-making and adaptive network formation without any central
control. 1024 autonomous agents deposit chemical trails, sense their environment through
three-sensor chemotaxis, and collectively produce emergent network structures.

This category contains five modules: the core simulation running on the GPU

\subsubsection{Slime Mold Simulation Module (M16)} \label{M16}

\paragraph{Secrets:}
The GPU compute shader implementation for simulating slime mold agent behaviour, including
three-sensor chemotaxis, trail deposition, ping-pong double-buffered trail processing

\section{Design of Communication Protocols}\label{SecDCP}

\subsection{Inter-Module Communication}

The system uses Unity's component-based architecture for module communication.
In Unity, game logic is attached to scene objects via \texttt{MonoBehaviour} scripts.
The engine automatically calls certain lifecycle methods on these scripts.
\texttt{Update()} is called once per rendered frame for per-frame logic.
\texttt{FixedUpdate()} is called on a fixed physics timestep (configured in \hyperref[M2]{M2})
for physics-dependent logic. \texttt{OnCollisionEnter2D} is invoked when two
physics colliders first make contact. These callbacks form the backbone of Unity's
event-driven communication model and are standard Unity engine functions; they are
not defined within this system's modules but are provided by the Unity engine itself.

\paragraph{Event-Based Communication:}
\begin{itemize}
\item \textbf{Input Events:} Unity's Input System generates events for mouse clicks, movement, and jumps when the corresponding hardware is activated.
\item \textbf{Collision Events:} The Physics2D system (\hyperref[M2]{M2}) invokes \texttt{OnCollisionEnter2D} on the relevant \texttt{MonoBehaviour} components when two colliders make contact. This is used to trigger debris interactions.
\item \textbf{Frame Events:} The engine loop calls \texttt{Update()} on every active \texttt{MonoBehaviour} once per rendered frame, and \texttt{FixedUpdate()} on the fixed physics timestep. These drive continuous per-frame and per-physics-step behaviour in modules such as \hyperref[M5]{M5} and \hyperref[M16]{M16}.
\end{itemize}

\paragraph{Direct Method Calls:}
\begin{itemize}
\item \hyperref[M6]{M6} (Raycast Visualization) calls \hyperref[M7]{M7} (Cut Execution) via \texttt{ExecuteCut()}
\item \hyperref[M7]{M7} calls \hyperref[M11]{M11} (Polygon Partitioning) via \texttt{PartitionPolygon()}
\item \hyperref[M7]{M7} calls \hyperref[M8]{M8} (Debris Generation) via \texttt{SpawnDebris()}
\item \hyperref[M9]{M9} (Cut Profile Manager) is accessed via static extension method \texttt{GetCutProfileForObject()}
\end{itemize}

\paragraph{Component References:}
\begin{itemize}
\item Modules get references using \texttt{GetComponent<T>()} for same-GameObject communication
\item Modules use \texttt{FindObjectOfType<T>()} for singleton manager access
\item Parent-child relationships use \texttt{GetComponentInChildren<T>()}
\end{itemize}
